# ForgeFlow ERP

ForgeFlow is an original manufacturing ERP for small and midsize discrete manufacturers:
inventory with lots and locations, multi-level BOMs and engineering changes, work orders,
MRP, purchasing, sales fulfillment, quality (NCR, holds, CAPA), operational finance and
reports — on one shared PostgreSQL database, so every transaction updates related records and
the dashboard immediately.

It is inspired by capabilities that integrated manufacturing ERPs describe publicly. All code,
branding, data models and UI are original; it is **not** affiliated with, endorsed by, or
compatible with any commercial ERP product.

> **Demo software.** The bundled data is fictional (Northstar Precision Manufacturing and
> Cobalt Ridge Fabrication), generated by replaying sample transactions — it is not live
> telemetry. ForgeFlow is not validated for regulated production (no FDA, ISO 13485 or
> 21 CFR Part 11 claims), and its finance views are an operational sub-ledger, not GAAP
> financial statements.

## Quick start (local demo, no accounts needed)

Requirements: Node.js 20.9+ (22 LTS recommended) and npm.

```bash
npm install
npm run dev
```

Open <http://localhost:3000> and pick a persona. The first start creates an embedded
PostgreSQL database (PGlite) in `.data/pglite` and seeds ~180 days of history ending today;
this takes about a minute. Later starts are instant. To start over, use
**Settings → Data & environment → Reset demo data** (admin) or run `npm run db:reset` while the
dev server is stopped.

## Demo walkthrough — the four core workflows

1. **Receive 60 of 100 with a lot** — as Sam: *Purchasing → Receiving*, open the Granite Peak
   Sensors order for 100 × RTD-PT100, click **Receive**, enter 60 and a lot number, post. The PO
   becomes *Partially received* (40 open), the lot appears under *Inventory → Lots*, the ledger
   gets a receipt movement, a GRNI journal posts, and the dashboard's inventory value moves.
2. **BOM → work order for 10 → issue → 5 good + 1 scrap** — as Riley: *Production*, open the
   released FG-CALKIT order for 10 (its BOM revision is frozen on the order), **Issue materials**
   (allocated quantities are pre-filled), then **Record output** with 5 good and 1 scrap. Stock,
   WIP, finished-goods lots, yield and the order's progress update together. New orders are
   created from *Production → Create work order* or from MRP suggestions.
3. **Sales order → reserve → partial ship → invoice** — as Sam or Taylor: *Sales orders*, search
   `LMD-PO-88412` (stock already reserved), **Ship** 12 of the 24 ECM-100s. The order becomes
   *Partially shipped*, a draft invoice is created by the organization's auto-invoice policy,
   and as Morgan you **Issue** it under *Finance → Invoices* (AR and revenue update).
4. **NCR hold blocks issue → authorized release** — the PROBE-REF lot under NCR is on quality
   hold, so the high-priority FG-CALKIT order reads *Blocked (hold)*: automatic picking skips the
   lot and selecting it explicitly is refused. As Casey: *Quality → Quality holds* → **Release**
   with a written justification (recorded with before/after state in the audit trail). The order
   becomes ready and the lot can be issued.

Every step is covered by automated tests (see *Testing*).

## Architecture

Next.js 16 (App Router, server components and server actions) · TypeScript · Tailwind CSS 4 ·
shadcn/ui · Recharts · TanStack Table · Zod · PostgreSQL (Supabase in production, PGlite for the
local demo) · Vitest · Playwright.

- `supabase/migrations/` — schema, constraints (no negative stock, received ≤ ordered, shipped ≤
  ordered), append-only ledgers, BOM cycle prevention, balanced-journal trigger, row-level security.
- `src/server/services/` — every business transaction: authorize → validate → lock rows →
  post inventory movements → journal → audit, in one database transaction, with idempotency keys
  for receipts, issues, output and shipments.
- `src/server/queries/` — read models for the dashboard, lists, details and reports.
- `src/lib/domain/` — pure engines (BOM explosion and roll-up, MRP) with unit tests.
- `src/server/seed/` — replays six months of operations through the same services.

Details: [`IMPLEMENTATION_PLAN.md`](IMPLEMENTATION_PLAN.md) · data model:
[`docs/ERD.md`](docs/ERD.md) · open work: [`NEXT_STEPS.md`](NEXT_STEPS.md).

  MRP netting and pegging, the four workflows end to end against Postgres, negative-stock and
  over-receipt rejection, idempotent resubmission, append-only ledgers, balanced journals, role

## Configuration

Copy `.env.example` to `.env.local`. With no variables the app runs in local demo mode.

| Variable | Purpose |
| --- | --- |
| `DATABASE_URL` | PostgreSQL connection string (Supabase). Unset = embedded PGlite demo |
| `AUTH_MODE` | `demo` (persona picker) or `supabase` (email/password via Supabase Auth) |
| `SESSION_SECRET` | Signs demo session cookies — required for any shared deployment |
| `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Supabase project (auth mode `supabase`) |
| `DATABASE_POOL_SIZE`, `DATABASE_PREPARE` | Pool size; prepared statements (keep `false` behind a transaction pooler) |
| `AUTO_MIGRATE` | Migrate and seed on first request when using `DATABASE_URL` |
| `ALLOW_DEMO_RESET` | Allow wiping a Postgres database from Settings or `db:reset` |
| `PGLITE_DATA_DIR` | Embedded database directory (default `.data/pglite`) |

## Deploying

### Supabase + Vercel (recommended)

1. Create a Supabase project (any region close to your users). Copy the **Session pooler**
   connection string (Connect → Session pooler, port 5432) and the project URL and anon key
   (Project Settings → API).
2. Apply the schema and load the demo data from your machine (about two minutes):
   ```bash
   export DATABASE_URL="postgresql://postgres.<ref>:<password>@aws-0-<region>.pooler.supabase.com:5432/postgres"
   npm run db:migrate
   npm run db:seed        # optional: the fictional demo tenants
   ```
   The seed generates the 180-day history in an in-memory database and copies it in bulk
   (about 20,000 rows in under a minute), so it does not depend on network latency. Migrations
   are plain SQL in `supabase/migrations`; `supabase db push` applies the same files.
3. Import the repository in Vercel and set environment variables: `DATABASE_URL` (pooler URL),
   `DATABASE_PREPARE=false`, `DATABASE_POOL_SIZE=3`, `SESSION_SECRET` (random 32+ bytes),
   `AUTH_MODE` and, for real accounts, `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY`.
   To skip step 2, set `AUTO_MIGRATE=true` instead: the first request migrates and seeds an
   empty database (it takes about a minute, so open `/api/health` once after deploying).
4. Deploy. `GET /api/health` should return `{"ok":true,"database":"postgres"}`.

If you can only reach the database through the Supabase SQL editor, apply the two migration
files there, then generate SQL inserts locally with `scripts/export-demo-sql.ts` (see its header)
and run them in name order.

To keep a hosted demo fresh, set `ALLOW_DEMO_RESET=true` on that deployment so an admin can
regenerate the data (dated to the current day) from **Settings → Data & environment**. Never set
it on a database with real data.

For real sign-in set `AUTH_MODE=supabase` and create users in Supabase Auth with the same email
addresses as ForgeFlow members (seeded people use `@northstar.example`; add your own under
**Settings → Members**). On first sign-in the auth user is linked to the matching profile.
`AUTH_MODE=demo` lets anyone with the URL pick a persona — use it only for public demos with
fictional data.

### Single server or container

`npm ci && npm run build && npm start` on any Node 20.9+ host. Without `DATABASE_URL` the embedded
database lives in `PGLITE_DATA_DIR`; put it on a persistent volume and run one instance only
(PGlite is single-process). Serverless platforms need `DATABASE_URL`, because their filesystem
is not persistent.

## Security notes

- Authorization is checked in the service layer for every write and in queries for reads; the UI
  only mirrors it. Every query is scoped by organization; cross-tenant access is covered by tests.
- RLS policies give members read-only access to their organization's rows when the database is
  reached directly with the anon key; there are no client write policies.
- Secrets come only from environment variables; `.env*` files are git-ignored except the example.
- Audit events, inventory movements, receipts, issues, shipments and journals are append-only at
  the database level.
